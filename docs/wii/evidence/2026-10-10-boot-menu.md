# Booting through the original menus into an environment (HWI-016D)

The Wii engine build now boots into the game's own main menu. It does not
load a map directly. With `boot.txt` on the card, the driver runs the engine's
own `main`: `shell_initialize`, then `main_loop`. That loads the UI map and
runs the interface's own widget code. The Wii rasterizer draws what that
code asks for: the widgets' bitmaps from the converted HWT1 textures, and the
text from the engine's own glyph cache, copied into a GX texture. A scripted
GameCube pad (an authored Dolphin movie, two ports) drives the menus. It
creates a profile, starts a two-player split-screen game and chooses Prisoner
from the menus' own map list. The engine then loads Prisoner and draws its
environment in both players' windows.

Prisoner is a multiplayer map. Every environment frame says so on screen:
`MAP PRISONER: MULTIPLAYER ENVIRONMENT (DIAGNOSTIC) - NOT THE CAMPAIGN`.

In stock Wii-mode Dolphin, two cold launches on each of two emulator hosts
gave the same game state at every sampled screen and at the environment. The
i686 Linux host reference, replaying each launch's pad, matched it too. The
one exception is the script threads' raw bytes in the menus (below).
[Numeric evidence](2026-10-10-boot-menu.json)

**Result:**

- **Menus:** 22 screens sampled on the way, from the main menu to the
  environment, all drawn by the engine's own widget code. A screen is
  sampled once it has stood for 45 frames: its EFB CRC and the game-state
  digests are logged.
- **Transition:** the menus' own map selection loads Prisoner at engine frame
  5,919. Its environment draws in two player windows for 150 frames, and the
  launch then ends with a pass.
- **Host comparison:** the environment's first and last game-state digests
  (`bf0caac3`, `98442fba`) equal the host's in all four launches. All 77
  allocations equal the host's at the first environment frame. At every
  screen the state excluding script threads equals the host's (22 of 22).
  The whole state equals it from the multiplayer screens on (6 of 22). Before
  that, only the `hs thread` allocation differs (below).
- **Manifests:** the source image, the converter generation and each staged
  map's SHA-256 are hashed at boot, logged, and shown on the bottom line of
  every frame.
- **Load failures:** a missing UI map, a damaged UI map, a missing target
  map and a damaged target map each show an actionable error and leave the
  card unchanged. They use HWI-016C's refusal kinds (`not_staged`,
  `damaged`). The two target-map failures go back to the main menu, and
  the menus keep working.
- **Prisoner direct-load regression:** simulation `127656ef`, whole state
  `6d88af44` (all 18 runs), equal to the host's at every tick.

## What the menu path runs

| Part | What |
|---|---|
| `boot_main.c` (driver) | `boot.txt`; the manifests and the SHA-256 of each listed map; the UI map's error screens; the GameCube pad; the end of the launch |
| `boot_hooks.c` (both builds) | wraps the rasterizer back end that `main_loop` reaches; checks the menus' map choice before the engine commits; the frame clock; sound and movie start-up skipped |
| `render_ui.c`, `render_ui_gx.c` | each player window's environment from its own camera, then `render_ui_widgets`; screen quads by bitmap tag and index; the engine's own text and glyph cache |
| `wii_xinput.c` | XInput on the GameCube pad |
| `wii_loopback_net.c` | in-process loopback sockets under the Linux port's `xnet.c`: the split-screen game's host and client |

**Drawn:** widget bitmaps (HWT1 from the generation, split-alpha CMPR with
its I4/I8 plane as a second TEV stage; a bounded 3 MiB texture cache with
66 loads and 8 evictions per launch); the engine's own glyph cache (128x128
A4R4G4B4, uploaded as IA4 before each character that dirtied it); button
icons; tint and fade. **Approximated, counted:** the interface's plasma
effect (the widget's own bitmap is drawn, 64,667 quads) and min/max blend
(the alpha blend; 0 used here). **Not drawn:** the HUD, the console, the game
engine's overlays, objects, sky and effects (see `UNSUPPORTED`). One UI bitmap
(tag 1642, bitmap 1) is not in the converter generation, so it is not drawn,
and the miss is logged (`BOOT_UI_TEXTURE_FAIL`).

**Input implemented:** GameCube A/B/X/Y to the XInput A/B/X/Y buttons; Start
to Start; Z to Back; the D-pad; the main stick to the left thumbstick; the C
stick to the right thumbstick; L/R analog to the triggers. Not mapped: the
black and white buttons and the thumbstick clicks. Each port reads `PAD_Read`.
A missing controller resets the port; any other transient error keeps the
last state, so a controller stays connected.

**Engine fixes for big-endian:** these were found on the menu path. Each is
small and commented, and the other ports are unchanged.

- the gametype list's count, read as a word through a long pointer;
- network message sizes, which read the short member of a short/long union
  (`network_messages.c`, `key_agreement.c`);
- the start request's countdown, a short copied from a long;
- transport addresses, which now use `ntohl`/`htons` (`transport_endpoint_*`);
- `xnet.c`'s byte-swap macros, which assumed little-endian;
- `ui_widget.c`, which now gives the port the active screen.

## Reproducibility

The frame clock is the default. `main_update_time`'s wait advances a clock
of the boot mode's own. `rand` is the Xbox C library's generator. The
calendar is a fixed date. A worker thread's exit is waited on in clock time.
Each launch is cold: a fresh Dolphin profile and the same clean card image,
with the same authored movie (81 steps, 33,336 polls on two ports, script
SHA-256 `118078da…`).

Each launch's guest, persistence, host and OS records are kept separately:

- **Guest:** the engine log ends `result=pass` (`environment_reached`).

allocation digests and frame numbers. Across hosts the game state is

## Host comparison

`run_boot_host.py` builds the same engine units for i686 with a GX side that
draws nothing. It replays each Wii launch's pad scan by scan, and its arena
placement. Every one of the four evidence launches was replayed:

| Comparison | Result |
|---|---|
| Screens sampled at the same frames | 22 of 22 |
| State without script threads equal | 22 of 22 |
| Whole state equal | 6 of 22 (every screen from frame 4,310 on) |
| Environment, first and last frame | equal (`bf0caac3`, `98442fba`) |
| Allocations at the first screen | 76 of 77 equal; `hs thread` differs |
| Allocations at the first environment frame | 77 of 77 equal |

The `hs thread` allocation is the script runtime's thread stacks. In the
menus, its raw bytes differ between PowerPC and x86 where a short script
value is stored in a long stack cell: the same value lies at the other end of
the cell. The allocation is equal again once the menus' scripts are no longer
running (frame 4,310 on), and at the environment. The state digests without
script threads equal the host's throughout. No canonical form for script
stacks exists yet in the boot digest (HWI-016C's canonical digest is the
map run's).

## Manifests

- **`manifest.txt`** (`boot_stage.py`): the source image's SHA-256
  (`43ec0813…`), the converter generation (`6e7b87372c08e3fa`, HWI-008F's
  split-alpha profile), the stager's SHA-256, and the UI textures staged
  (384 files, 20,142,784 bytes).
- **`data/maps/manifest.txt`** (`map_stage.py`, HWIMAP02): a line per staged
  map with its format, bytes, staging digest and SHA-256:

  | Map | Bytes | Staging digest | SHA-256 |
  |---|---|---|---|
  | `prisoner` | 7,988,984 | `3189bf32` | `fecad67a…` |
  | `ui` | 1,672,288 | `ec1bd32a` | `a8453c41…` |

At boot, each listed map is hashed: 857 ms of guest time for 9.7 MB. The
results go to the SD log as `BOOT_MANIFEST` lines. The bottom line of every
frame shows the build, the source, the generation and each map's SHA-256
prefix. A map that fails its hash is marked `!`.

## Load failures

Each failure test is a cold Titan launch from its own card image.
`expect=refusal` passes a launch once a map was refused and the menus' map
loaded again.

| Test | Card | Kind | What the screen shows | Engine frame / EFB CRC | Result |
|---|---|---|---|---|---|
| UI map missing | `ui.wmap` removed | `not_staged` | Boot error screen (built-in font): the file to copy, the command that stages it, and that nothing was changed and the game did not start | 30 / `3c44459c` | pass |
| UI map damaged | 16 bytes of `ui.wmap` changed | `damaged` | Boot error screen: the file, that its bytes differ from the manifest, and how to stage it again | 30 / `0400b90b` | pass |
| Target map missing | `beavercreek` chosen, not staged | `not_staged` | The engine's own error dialog with the map, the kind and the tool to stage it; then the main menu | 4,818 / `fcd842ec` | pass, recovered |
| Target map damaged | 16 bytes of `prisoner.wmap` changed | `damaged` | The engine's own error dialog (the map does not match its manifest; stage it again); then the main menu | 5,380 / `67f3bd37` | pass, recovered |

A refused target map is refused when the menus choose it, before the
precache or the network game commits. The engine's own failure path follows:
the game ends and the main menu loads again. The menus then keep running:
the profile screen is sampled after it in both tests. The UI map tests end
before the engine starts. No test writes anything to the card except the
log and the counters. Persistence reports `failed` for the two UI map tests
only because the engine's `debug.txt` is never created when the engine does
not start.

## Remaining work

- The interface's plasma effect is not composited, and min/max blend is
  approximated. The HUD, the console, objects, the sky and effects are not
  drawn in the boot mode.
- One UI bitmap (tag 1642, bitmap 1) is missing from the converter
  generation.
- Sound and movies are not started (`sound_initialize` and
  `bink_playback_start` are skipped in the boot mode).
- System link and internet play are absent. Split screen runs over the
  in-process loopback.
- The input mapping is minimal: no black or white button and no thumbstick
  clicks.
- Script thread stacks have no canonical digest. Raw bytes differ from the
  host in the menus (above).
- A launch creates a profile on its card, so the cold launches use separate
  copies of the same clean image. Running twice on one card would follow a
  different menu path.
- The render module's generic `UNSUPPORTED` list still names menus and text,
  which the boot mode now draws.
- The campaign itself (a10) is not reached from the menus. Prisoner is
  labelled as a multiplayer diagnostic environment.
- No physical Wii was used.

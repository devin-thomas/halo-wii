# Asset-free native GX scene (HWI-014A)

The first native GX rendering result: an authored colour cube, an intersecting
satellite cube, a checkered floor and a bitmap HUD, driven by controller input.
No game data is used. [Numeric evidence](2026-10-10-gx-scene.json)

## Stock Dolphin, Wii mode

A new isolated profile ran stock clock and memory, no cheats, overclock or RAM
override, D3D at 1x, and CPU EFB access enabled. An authored DTM drove a
standard GC pad on port 1; this is virtual input. Two cold launches shared one
emulated SD image.

| Outcome | Run 1 | Run 2 |
|---|---|---|
| Guest scope | pass | pass |
| EFB self-checks | 9/9 | 9/9 |
| Input (yaw/pitch/zoom/spin/reset/START) | all observed | all observed |
| Launch counter read back | 1 | 2 |
| Prior log preserved | n/a | yes |
| Host exit | 0x0, natural | 0x0, natural |
| Forced stop | no | no |

**Rendering checks.** Eight fixed poses are rendered into the EFB and read back
from the CPU. They confirm the front face at screen centre, the backdrop, the
clear colour, the top face under positive pitch, the left face under positive
yaw, and that the cube is nearer than the backdrop in Z. Two controls must change
the answer, and both did: with culling off, a back-facing quad becomes visible;
with depth testing off, the backdrop overdraws the cube. Frame dumps, 430 per
run, show the scene, the build ID and the input-driven pose changes. The frames
stay local; three are identified by hash in the JSON.

**Owned resources.** The guest registers and logs every buffer GX or VI reads.
All are 32-byte aligned in MEM1 and validated against overlap:

| Buffer | Bytes | Cache policy |
|---|---|---|
| GX FIFO | 262,144 | zeroed, then `DCFlushRange` before `GX_Init` |
| XFB 0 / XFB 1 | 614,400 each | K1 uncached; written only by GX copy |
| Cube positions | 128 | filled, `DCFlushRange`, `GX_InvVtxCache` |
| Cube colours | 32 | filled, `DCFlushRange`, `GX_InvVtxCache` |

Measured in this scenario:
- CPU FIFO submission averages 23,596 bytes per frame, peaking at 24,608 (PI
  write-pointer delta, excluding the EFB copy).
- CPU submit plus `GX_DrawDone` takes 69–82 µs; the frame interval is
  16.42–16.70 ms.
- Heap use is 1,669,664 bytes after initialisation, with zero growth during the
  loop.
- The deepest sampled stack is 120 bytes below the entry frame. This is a sample,
  not a peak.

**Host and OS.** Both runs exited the Dolphin host naturally with 0x0. During
both runs the Windows event logs show no bugcheck, Kernel-Power or
unexpected-shutdown events, and no Dolphin application fault or hang events.
That covers this session only. The exit result is scoped to this DOL and
configuration. It does not resolve the deferred original-probe teardown fault
(HWI-050).

## Development iterations (dirty source, retained)

The first launch failed its guest scope while the host exited 0x0. Every EFB
peek returned zero because CPU EFB access was not enabled in the fresh profile.
The DTM input was also ignored: Dolphin derives a DOL's game ID from its file
name, so the reused `ID-pro` header did not match `ID-gx_scene`. In the same
iteration, the libogc FIFO count stayed at zero and was replaced by the PI
write pointer, and a one-time 200-byte newlib float-formatting allocation was
moved before the heap baseline. The second launch, with `EFBAccessEnable` and
DTM ID `ID-gx_`, passed.

## Not established

- Physical Wii behaviour: hardware cache/DMA coherence, VI output on a display,
  GP throughput and controller latency.
- Textures, materials, alpha, mipmaps and lighting. These remain in HWI-014.
- Halo asset rendering, engine integration, gameplay and whole-engine memory
  feasibility.
- GP FIFO occupancy peak and stack peak.

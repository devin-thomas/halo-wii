# a10's simulation, independent of the render cadence (HWI-016F)

HWI-016C ran the campaign map a10 for 9,000 ticks at 30 Hz, 60 Hz and paced
by the measured vertical retrace. Each cadence equalled the i686 host tick
for tick, but the cadences differed from each other in effects, particles,
sounds and objects. This ticket traced every difference to its field and its
writer, classified each, and fixed the ones that are simulation state.

The game state's simulation now runs the same at every render cadence: on
a10, at 30 Hz, 60 Hz and the Wii's measured retrace, the simulation digest
is identical after every one of the 9,000 ticks, and each cadence still
equals the i686 host tick for tick. On the host this also holds at 20 Hz,
144 Hz and an irregular cadence with a 0.5 s hitch. At 30 Hz, a frame a
tick as on the Xbox, no fix changes gameplay timing. The one change there is
which of the clock-seeded local random numbers a tick draws (below).
[Numeric evidence](2026-10-11-a10-cadence.json)

**Result:**

- **First divergence:** tick 3 of the simulation digest, in the object
  looping sounds: element 134's `last_audible_frame_index` (offset 0x14)
  is 1 at 30 Hz and 4 at 60 Hz. Bisected on the host, then found in the
  HWI-016C Wii logs at the same allocations and checkpoints.
- **Simulation that depended on the cadence, fixed on every port:**
  - The game ticks and the frames drew from one stream of local random
    numbers. The frames' particles, contrails and sounds draw from it, so a
    frame without a tick, or with two, moved the numbers that the ticks'
    effects then drew. The effects' event lengths and particle counts
    changed, then the effects they made, then the effect handles that
    objects keep (from tick 52; objects from tick 6,971). The ticks now draw
    from a stream of their own.
  - The main loop handled the game's requests once a frame: a checkpoint
    save, a script's structure BSP switch, a respawn. The save also counted
    its tries per frame. A frame of several ticks moved a10's opening
    checkpoint from after tick 1 to after tick 3. These requests are now
    handled between the ticks of such a frame, and the save counts ticks.
  - At a new map, the PVS activation's union kept the previous run's object
    (a run's history, not its cadence). It is now cleared with its type.
- **Presentation, classified with every reader traced:** the object
  looping sounds, and the scenario's fog and sound environment fields.
- **Regressions:** Prisoner keeps simulation `127656ef` under HWI-015B's
  classification, and HWI-015A's scenario keeps `c1ad6ae6`. Prisoner's
  whole state moved from `6d88af44` to `7eb53576` on both sides, solely
  because of the tick random stream, in two frame-coupled allocations
  (below).
- **Dolphin:** two cold launches each on Titan (D3D) and the Research
  Mac (Vulkan). In every launch a10's three cadences give the same
  simulation at every tick (`f752db70` at the end), and all 28 run lines
  equal the i686 host's, whole state included. Titan's and Research's
  digests are identical but for the frame-coupled state of the
  retrace-paced run, whose frame times each host measures. Research's
  first launch ended with a Dolphin host fault at shutdown (`0xfffffffb`,
  after the guest's `END result=pass`), recorded below.

## How the divergence was found

The host reference (`tools/wii/run_engine_map_host.py`) runs the Wii's run
on the i686 host in about a minute. Two plan lines ran a10 for 9,000 ticks,
one at 30 Hz and one at 60 Hz, each after its own 30-tick warm-up. A new
diagnosis, `trace:<allocation indices>` (`engine_map_run_set_dump`), logs
those allocations' raw digests after every tick, so the first differing tick
of each allocation is found in one run. Whole-state dumps at that tick name
the element and field, by the engine's own structure layouts.

Before any fix (the base `186343a6`; host, 30 Hz against 60 Hz):

| Allocation | First tick | Ticks differing | Field |
|---|---:|---:|---|
| object globals | 1 | 61 | `pvs_activation` union (offset 0x94): 0 against a previous run's object |
| object looping sounds | 3 | 8,998 | element 134, `last_audible_frame_index` (0x14): 1 against 4 |
| effect | 52 | 8,949 | element 3, `event_duration` (0x54) and `particle_counts` (0xDC); element 5 made only at 60 Hz |
| effect location | 3,634 | 5,367 | the effects' locations, made with them |
| objects | 6,971 | 2,030 | three objects' effect attachment handles: identifiers from 0x92f2 against 0x9322 (48 more effects made at 60 Hz) |

The simulation digest (HWI-015B's classification) first differs at tick 3.
The HWI-016C Wii logs show the same allocations differing at the same
checkpoints (object looping sounds from tick 30, effect from tick 150,
objects and effect locations at the end), so the Wii confirms the host's
picture without another launch.

With the tick stream (below), the effects, effect locations and objects are
equal at every tick. Three more differences then showed, with the other
cadences:

| Found | Where | Cause |
|---|---|---|
| Scenario globals at tick 1,513 | Its sound environment (offset 0xB8 on) | Steps toward the camera's cluster's environment once a frame |
| Object looping sounds at 20 Hz, tick 1,513 | A background sound's index | Started by the frame after a BSP switch, so it takes its index a tick later at 20 Hz |
| Everything from tick 2, retrace-paced | a10's opening checkpoint | Saved after the frame's ticks: after tick 1 at 30 Hz, after tick 3 when the first frame ran three |

## Classification

### (b) Simulation state that depended on the cadence: fixed

The original engine has each of these: the i686 host shows the same
differences by construction, and the code is the engine's own. On the Xbox
a frame was a tick, one `game_frame` after each `game_tick`, so they did not
show except when a frame ran late.

| Field | Writer | Readers that make it simulation | Fix |
|---|---|---|---|
| The ticks' local random numbers (`random_math.c`), so effect `event_duration`, `particle_counts`, the effects and objects made from them | Per frame: `particles.c:481-994`, `particle_systems.c:590-1175`, `contrails.c:187-882`, `lightning.c:244-553`, `wind.c:222-236` | `effects.c:2382` (whether an event runs), `effects.c:2416`, `2846` (its length), `effects.c:1702` (`object_new` from an effect part), `effects.c:1738` (damage), `objects.c:3351` (an object keeps the effect's handle), `model_animations.c:708` | The ticks draw from their own stream: `game_time.c:475-478`, `random_math.c:149-199`, `218` |
| The checkpoint save's tick, a BSP switch's, a respawn's | Once a frame: `main_loop` (`main.c`), and `main_save_map_private`'s tries counted per frame (`main.c:1967`, `1975`) | `game_state_save` (`main.c:1951`) and the switch and respawn themselves | Between the ticks of a frame that runs several (`main.c:3255`, `game_time.c:471-474`); the save once per tick (`main.c:3237`, `3490-3495`) |
| `object_globals->pvs_activation` union (history) | `objects.c:518`, `554`, `571` | None while the type is normal (`objects.c:588-617`); it entered the digest | Cleared at a new map (`objects.c:1086`) |

At 30 Hz:

- **The random streams.** At every frame the local random seed is the
  clock's (`random_math_initialize`), so no value of it is the game's, and
  every draw is from the same distribution as before. What changes is which
  numbers a tick draws, not how the game uses them; the global random
  numbers the simulation shares are untouched. Prisoner's simulation is
  bit-identical (`127656ef`).
- **The requests.** A frame of one tick never runs the new between-ticks
  handling, and its save still runs once after it.
- **The union.** No reader reads it while the type is normal.

A frame that ran late on the Xbox (two ticks in one frame) is now handled as
two frames of one tick would be. That is the cadence invariance itself.

### (a) Presentation only: joined the frame-coupled class

| Field | Writer | Every reader | Why it is presentation |
|---|---|---|---|
| object looping sounds (the allocation) | `game_sound.c:357-416` (objects, scripts: their sounds), `game_sound.c:820-905` (once a frame: state, frame index, the background sound, deleting the sounds that played out) | `game_sound.c:1183-1306` (state, `last_audible_frame_index`, to the sound manager), `game_sound.c:285-340` (save/restore), `game_sound.c:668-800` (the scripts' sound commands); handles kept by `objects.c:3336-3348` and `5012` (attachments) and the looping sound definition's `runtime_scripting_sound_index`, read back only by `game_sound.c` | Only the game's sound reads a looping sound. The handles that objects keep only pass back to the game's sound |
| scenario globals from `atmospheric_fog` to the end (offsets 0x04-0x100): fog per local player, the sound environment | `scenario.c:1369-1400` (once a frame, from `game_sound.c:829`), `scenario.c:1488-1536` (per drawn view, from `render.c:455`) | `game_sound.c:833` → `sound_manager.c:846`; `render.c:455` (the fog of the view) | Sound and drawing only; the structure BSP index before them stays in the simulation |

The simulation's digest reads these fields as zeros (`frame_coupled_fields`,
`real_map_scenario.c`); the whole state keeps them. The looping sounds join
HWI-015B's frame-coupled allocations.

The looping sounds keep one residual: a background sound started by a frame
takes its index from the same array that objects' sounds do. An object
made in the tick before that frame would keep a different index (only the
game's sound reads it back). This did not happen in a10. Each run counts the
datums frames make in the arrays the ticks also use (`frame_effects`,
`frame_sounds`): a10 makes 0 effects and 1 background sound by frame, at
every cadence.

## The harness

- **Order:** a line's cadences run 30 Hz first, so each line's reference
  run is the game's own cadence.
- **Two simulation digests:** `sim` is HWI-016F's classification. RUN lines
  also carry `sim_hwi015b`, HWI-015B's (the looping sounds and the scenario
  fields kept). `expect=` checks HWI-015B's, so Prisoner's `127656ef` stays
  checkable; `expect_sim=` checks HWI-016F's (Prisoner `961a5ec5`).
- **Comparison:** `compare_map_runs.py` reports each log's cadence
  invariance per map, and compares `sim_hwi015b` and the frame counts
  between the Wii and the host.
- **a10's line** now fails a run whose simulation differs (`invariance=1`,
  the default).

## Not covered

- **Revert, a loss, a core load, a won map:** still handled once a frame.
  A frame of several ticks runs its remaining ticks before them, and those
  ticks draw the tick random stream, which a revert does not restore. Not
  reached in a10's 9,000 ticks; see the decision below.
- **The main loop's camera and input:** `director_update`,
  `observer_update` and `player_control_update` run once a frame
  (HWI-016B lists what they feed). The run gives every tick its input and
  draws nothing, so they are not exercised.
- **Effects made by particles:** a particle's death or collision effect is
  made by a frame. a10 makes none in 9,000 ticks (counted); another map can.
- Physical Wii untested.

## Cross-port scope

The three engine fixes are deliberately cross-port: `random_math.c`,
`game_time.c`, `main.c`, `main.h`, `real_math.h` and `objects.c` are shared
by the Linux, Android and Windows ports. Those ports draw frames at the
display's rate (`render_interpolation.c`), so their simulation had the same
dependence on frame rate; it now has none, and at a frame a tick nothing
changes. Their particles, contrails and sounds keep moving every frame, as
before. The harness changes are Wii-only (`port/wii/engine`,
`tools/wii`).

## Decision for Devin

One choice is left open, because each way changes what the original does
when a frame runs late:

- **Revert, loss, core load, won map in a frame of several ticks.** The
  original runs the frame's remaining ticks, then reverts at the next
  frame. The game state the revert restores is the same either way, but
  those extra ticks draw the tick random stream, which the original does
  not save. So after a revert, the local random numbers (effects' event
  lengths, idle poses) depend on how many ticks the frame had left.
  - **(A) Leave it** (now): a revert is a player-visible transition, and
    only local random numbers differ after it.
  - **(B) Stop the frame's ticks** when one of these is asked for. This
    needs the update queue's backlog carried over (`player_queues_new.c`),
    not dropped.
  - **(C) Save the tick stream's seed** with a checkpoint and restore it
    with a revert. The original never restores the local seed.
